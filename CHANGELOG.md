## [Unreleased]

### 🔌 Клиент GraphQL Data API (`core/graphql_api.py`) — шаг 1 планировщика v2

- `prices_one_way` отдаёт **все** билеты на дату (а не один самый дешёвый на
  направление, как REST `prices_for_dates`): сегменты с аэропортами и временами,
  длительность каждой пересадки (ночная, виза), багаж явным полем. Работают
  «город → ANY» и «ANY → город». Страницы по 400, 60 запросов/мин, ценовой
  коридор `value_min/value_max`.
- Нормализованный билет — надмножество «сырого рейса» REST (те же `origin`,
  `departure_at`, `duration`, `transfers`, `price`, `link`…), плюс реальный
  `arrival_at`, `duration_to` (в воздухе), `chain`, `legs`, `transfer_points`
  с минутами, `baggage`. Цепочка учитывает смену аэропорта на пересадке
  (IST→SAW). Длительность — по сегментам (`trip_duration` источника = 0).
- Кэш серий `ticket_cache` (направление × день × коридор, TTL 24 ч, обрезанная
  серия переиспользуется только при достаточной глубине); `/api/health` отдаёт
  `ticket_series`. CLI `scripts/fetch_tickets.py MOW - 2026-10-15 --max 40000`.

### 🧭 Только планировщик: запрос → наборы → маршруты — шаг 5 планировщика v2

- Классический поиск «туда-обратно» (`/`, `/results`) удалён; планировщик живёт на `/`.
- Единый запрос до загрузки: скелет + фильтры городов, плеч (пересадки, мин.
  ожидание, багаж, hidden-city, длительность), длина поездки, потолок цены и число
  маршрутов; всё в URL (`planner/query.ts`). Кнопка «Найти» → `POST /api/plan/run`.
- Если где-то «любой» или несколько городов — страница `/combos/:job` (наборы
  городов с бэка, сортировка, **чекбоксы**, «Показать маршруты выбранных →»),
  иначе сразу `/routes/:job` (страницы с бэка, «Показать ещё»). На страницах
  результата фильтры сворачиваемые: «Применить» запускает новый сбор.
- Убраны фронтовые вычисления: воркер наборов (`overview.ts`), клиентская
  фильтрация, компактный результат и кэш IndexedDB. `GET /api/plan/jobs/{id}`
  отдаёт только прогресс и сводку; граф рёбер (`overview_graph`) удалён.

### 🗺 Наборы городов на бэке — шаг 4 планировщика v2

- `core/overview.build_overview`: для каждой собираемой последовательности городов —
  минимальная цена, пересадки при минимуме, минимум пересадок, точное число
  цепочек. Динамика по префиксам с матрицами совместимости рейсов (numpy) по тем
  же правилам, что у перебора A* (дата, дни пребывания, окно, выходные, повторы,
  длина поездки); проверено перекрёстно с полным перебором. Считается в джобе
  (этап «Наборы городов»), без границ max_results/max_cost.
- `GET /api/plan/jobs/{id}/combos?sort=price|count|transfers&offset&limit` —
  страница наборов с именами городов. numpy добавлен в образ api.

### 🎛 Единый запрос с фильтрами и страницы маршрутов на бэке — шаг 3 планировщика v2

- `core/planquery.PlanQuery`: скелет + фильтры городов (дни, окно, выходные),
  плеч (пересадки, мин. ожидание на каждой пересадке, длительность, багаж
  any/included/none, hidden-city) и длины поездки одним объектом. Фильтры плеча
  режут рейсы до перебора, городов — внутри A* (пребывание между прилётом и
  вылетом кандидата), длина поездки — при выдаче. Отсутствующие фильтры открыты.
- `POST /api/plan/run` — запуск по PlanQuery; одинаковый запрос в пределах суток
  переиспользует готовую/идущую джобу (`reused`), в ответе `mode` (combos|routes).
  `GET /api/plan/jobs/{id}/routes?offset&limit&combos=MOW-IST-ICN,…` — страница
  маршрутов с полными сегментами, наборы городов — фильтром. Разобранные
  результаты двух последних джоб кэшируются в памяти.
- На карточке — бейдж багажа по билету («🧳 1 × 23 кг» / «без багажа»), у
  hidden-city — «!» с подсказкой.

### ✈️ Планировщик собирает через GraphQL — шаг 2 планировщика v2

- Город→город: пары A×B по одной странице в день (все билеты дня, прямые и с
  пересадками сразу). Плечо с «любым» концом: серия «город → ANY» / «ANY → город»
  с ценовым коридором `value_max = max_cost` и потолком 12 страниц в день (до
  4 800 самых дешёвых билетов). Оценка запросов = страницы (пессимистично, по
  потолку серии), прогресс сходится с ней ровно; `estimate.ts` синхронизирован.
- Hidden-city честно: из полного A→ANY, хаб — любая пересадка (не только первая),
  прилёт в хаб реальный (без «≈»), порог — лучший прямой A→B того дня. Для плеча
  «A → любой» hidden-city во все промежуточные хабы бесплатно. Карта
  аэропорт→город из накопленных `quotes` — закрыт пропуск PEK/PKX (SVO→PEK→SIN).
- Сегменты несут багаж (`segment.baggage`) и пересадки с ожиданием, ночной и визой;
  на карточке — ожидание у каждой пересадки. Виртуальные рейсы в `quotes` не пишутся.
- REST `prices_for_dates` остался только у сбора X→ANY (`core/anyscan`).

### 🧠 Планировщик: до 1 000 000 маршрутов без OOM

- Сборка на 100k маршрутов роняла api по OOM (VM 4 ГБ): каждая цепочка была
  словарём с копиями сегментов, результат — ~270 МБ JSON, а ручка статуса ещё раз
  разбирала и сериализовала его. Фронт видел «Потеряна связь с сервером».
- A* раскрывает узлы лениво: в куче только лучший невыданный ребёнок узла, путь —
  связный список индексов рейсов. Результат — компактный формат `compact-v1`:
  уникальные сегменты один раз + плоские массивы индексов/дней/выходных.
- Замер на стенде уровня прод-запроса (MOW → any → SEL → any → MOW): 100k —
  пик 6.1 ГБ → 134 МБ, JSON 265 → 3.8 МБ; 1M — 495 МБ, JSON 35 МБ.
- `/api/plan/jobs/{id}` отдаёт сохранённый JSON как есть (без `json.loads`).
- Фронт держит цепочки в typed-массивах, фильтрует по индексам и собирает карточки
  только для показанной страницы. Лимит маршрутов поднят до 1 000 000 (и на бэке).

### ⚡ Кэш под-запросов сбора (origin, destination, day)

- Ответы Travelpayouts по одному под-запросу `(origin, destination, day)` кэшируются
  в SQLite (`fetch_cache`) с TTL **24 часа**. Недавно собранные под-запросы не ходят
  в API повторно — экономия запросов при пересекающихся сборах (особенно ANY-плечи,
  общие между маршрутами и цепочками планировщика).
- TTL = 24 ч подобран под сам источник: Data API отдаёт кэш цен с задержкой ~суток,
  чаще перезапрашивать бессмысленно.
- Rate-limit пауза перенесена внутрь реального обращения к API — попадания в кэш её
  не платят. Сбойные ответы (ошибка сети) в кэш не попадают, честный пустой — попадает.

## [2.3.0] - 2025-12-01

### 🎯 Переходы между аэропортами по умолчанию

- **Переходы между аэропортами теперь включены по умолчанию**: Больше не нужно указывать `--enable-airport-transfers`
- **Новый флаг `--disable-airport-transfers`**: Позволяет отключить переходы между аэропортами, если они не нужны
- **Фильтрация по странам**: По умолчанию разрешены только переходы между аэропортами одной страны
- **Новый флаг `--allow-cross-country-transfers`**: Разрешает переходы между аэропортами разных стран

### 📊 Примеры использования

```bash
# По умолчанию - переходы включены, только внутри одной страны
poetry run python aggregate_flights.py data/flights_MOW_BKK.json

# Отключить переходы между аэропортами
poetry run python aggregate_flights.py data/flights_MOW_BKK.json \
  --disable-airport-transfers

# Разрешить переходы между аэропортами разных стран
poetry run python aggregate_flights.py data/flights_MOW_BKK.json \
  --allow-cross-country-transfers
```

### 🔍 Логика фильтрации

По умолчанию при поиске переходов между аэропортами система:
1. ✅ Разрешает переходы между аэропортами одной страны (например, SVO → DME в Москве, Россия)
2. ❌ Блокирует переходы между аэропортами разных стран (например, LED, Россия → HEL, Финляндия)
3. Показывает название города для каждого аэропорта в результатах
4. Отображает расстояние между аэропортами при переходе

## [2.2.0] - 2025-11-30

### 🚌 Новая возможность: Переходы между аэропортами

Добавлена поддержка поиска рейсов с учетом переходов между близкими аэропортами. Теперь можно найти комбинации, где вы прилетаете в один аэропорт, а улетаете из другого (например, прилет в SVO Шереметьево, вылет из DME Домодедово).

### ✨ Новые возможности

- **Построение сети аэропортов**: Новый скрипт `build_airport_network.py` загружает данные об аэропортах из публичного датасета HuggingFace и вычисляет расстояния между близкими аэропортами по GPS координатам
- **Поиск с переходами**: Флаг `--enable-airport-transfers` в `aggregate_flights.py` активирует поиск с учетом близких аэропортов
- **Гибкая настройка**: Параметр `--airport-distance` позволяет настроить максимальное расстояние между аэропортами (по умолчанию 100 км)
- **Автоматическая загрузка**: Сеть аэропортов автоматически строится при первом использовании, если файл отсутствует
- **Информативный вывод**: В результатах поиска отображается информация о переходах между аэропортами с указанием расстояния

### 📊 Статистика

- Загружено 9,103 аэропортов с IATA кодами из мирового датасета
- Построена сеть из 7,550 аэропортов с близлежащими соседями
- Среднее количество близких аэропортов: 5.5 на аэропорт

### 📝 Примеры

```bash
# Построение сети аэропортов вручную (опционально)

# Поиск с учетом переходов между аэропортами (до 100 км)

  --enable-airport-transfers

  --enable-airport-transfers --airport-distance 150
```

## [2.0.0] - 2025-11-30

### 🌟 Главное изменение: Автоматический поиск направлений

Добавлена поддержка нового подхода к сбору данных о рейсах. Теперь вместо ручного указания всех промежуточных аэропортов, API автоматически находит все доступные направления.

### ✨ Новые возможности

- **Автоматический поиск всех направлений**: Параметр `--intermediate` теперь опционален
- **Гибкие параметры API**:
  - `unique=true` - уникальные направления
  - `limit=1000` - до 1000 результатов за запрос
- **Опциональный destination**: Можно собирать только исходящие рейсы из города

### 📊 Сравнение подходов

#### Старый способ:
```bash
# Нужно вручную указать все промежуточные города
python collect_flights.py MOW BKK \
  --leg1-dates 2026-02-15 2026-02-20 \
  --leg2-dates 2026-02-25 2026-03-05 \
  --intermediate IST DXB AUH DOH

# Результат: 4 промежуточных города × 6 дат × 9 дат = 216 API запросов
```

#### Новый способ (рекомендуется):
```bash
# API сам найдёт все доступные направления
python collect_flights.py MOW BKK \
  --leg1-dates 2026-02-15 2026-02-20 \
  --leg2-dates 2026-02-25 2026-03-05

# Результат: 6 дат (leg1) + 9 дат (leg2) = 15 API запросов
# Найдено: ~150-200 направлений автоматически!
```

### 🎯 Преимущества нового подхода

1. **Меньше запросов**: 15 вместо 216 (экономия 93%)
2. **Больше направлений**: ~150-200 вместо 4 указанных вручную
3. **Проще использование**: не нужно знать промежуточные аэропорты
4. **Быстрее выполнение**: меньше времени на сбор данных

### 🔄 Обратная совместимость

Старый способ с `--intermediate` всё ещё работает и может быть полезен, если вы хотите ограничить поиск конкретными городами.

### 📝 Примеры

**Автоматический поиск всех направлений:**

```bash
  --leg1-dates 2026-02-19 2026-02-19 \
  --leg2-dates 2026-02-25 2026-02-25
```

```bash
  --leg1-dates 2026-02-19 2026-02-19 \
  --leg2-dates 2026-02-25 2026-02-25 \
  --intermediate IST DXB
```
