# Коллектор и Parquet-озеро

Билеты больше не живут в SQLite: их собирает отдельный сервис **коллектор** и
складывает Parquet-файлами в Object Storage. В SQLite остаётся только горячее
состояние (джобы планировщика, котировки, индекс серий коллектора).

```
web (Caddy) ──/api/*──> planner (api/)  ──POST /v1/fetch──> collector (collector/) ──> GraphQL Data API
                                                             │  очередь app > crawl, лимит 60/мин
crawler (crawler/) ──POST /v1/batch (crawl)──────────────────┘  │
                                                                └──> S3: tickets/fetched=<день загрузки>/origin=<город>/<A>-<B>__<дни вылета>__<время>.parquet
                                                                     индекс серий: data/collector.db (SQLite)
```

Образы: `deploy/Dockerfile.planner` (Rust), `.collector`, `.crawler` (Python) плюс
`flights-web`. Токен Travelpayouts нужен только коллектору; ключи S3 (общий `.env` VM) —
коллектору на запись и планировщику на чтение: склад билетов в памяти планировщика сам
читает файлы озера (`docs/TICKETS.md`).

## Фазы

1. **Коллектор и переход на S3** (этот документ): сервис, очередь с приоритетами,
   лимит ручки, озеро, индекс, ретеншн; планировщик ходит за сериями в коллектор;
   переименование `api` → `planner`; потолок бакета 200 ГБ.
2. **Фоновый сборщик** (`crawler/`): покрытие «город × день» на 180 дней вперёд,
   целевая свежесть по дальности даты, открытие новых городов из ответов, подача
   заданий в очередь `crawl`. Собираем только `X→ANY` (обратная сторона дублирует).
3. **Дашборды**: ops-метрики и снимок покрытия из коллектора в бакет, вьюхи
   ClickHouse и дашборд Grafana (папка «Flights») на аналитической VM Market Data.
4. **Отдельный репозиторий для аналитической VM** (terraform, compose, провижининг);
   проекты оставляют у себя только дашборды и SQL.
5. **Планировщик на данных озера**: без запросов к источнику из планировщика.
   Запуск — по решению, когда данных накопится достаточно.

## Коллектор (`collector/`)

- **Единица очереди — серия**: направление × день × прочие параметры (коридор цен,
  direct, багаж) — тот же ключ, что был у `ticket_cache`. **Единица работы — одна
  страница GraphQL** (400 билетов). После каждой страницы серия возвращается в
  очередь, и воркер берёт самое приоритетное задание: серия приложения (`app`)
  вытесняет фоновую (`crawl`) на границе страницы, та продолжает с того же offset.
- **Окно дат** (`day_to`, фоновый сборщик): один запрос `depart_date_min..max` вместо
  запроса на каждый день — источник отдаёт ровно те же билеты (проверено 30.09.2026), а
  платим минимум страницу за запрос. Готовое окно раскладывается по дню вылета
  (`departure_at[:10]`): в индексе — обычная строка на каждый день (страницы записаны на
  первый день окна), в озере — один файл на окно, row group на непустой день
  (`tickets/fetched=<день загрузки>/origin=X/X-ANY__<первый день>..<последний день>__<время>.parquet`).
  Планировщик по-прежнему спрашивает по дням и получает их из кэша.
- **Потолок offset** (~14 800) не обрезает серию: упёршись в него, коллектор
  продолжает тот же запрос с `value_min` = цена последнего билета (сортировка по цене),
  билеты на границе цены отсекаются по ссылке. Предохранитель — `COLLECTOR_MAX_PAGES`
  (100 страниц = 40 000 билетов на задание, память воркера).
- Одинаковые серии от разных клиентов **склеиваются** в одно задание (приоритет
  поднимается до `app`, глубина — до максимальной из запрошенных).
- **Кэш**: свежая серия из индекса (моложе `SERIES_TTL_SECONDS`, по умолчанию сутки;
  для обрезанной серии — не меньше страниц, чем просят) отдаётся без источника —
  из буфера или чтением своей row group из Parquet (файл из S3 — одним GET).
- **Лимит ручки** (`collector/ratelimit.py`): ровный темп `RATE_PER_MINUTE` (60).
  На 429 — пауза `Retry-After` либо бэкофф 5 → 10 → … → 60 с, затем две минуты
  темп в полтора раза ниже. Сетевые ошибки — три повтора страницы, ошибка источника
  (400: неизвестный город и т.п.) — серия помечается `error` и кэшем не считается.
- **Озеро** (`collector/lake.py`): один файл на выборку (день или окно дат), путь =
  **день загрузки + город запроса**, в имени — направление, дни вылета, параметры и время:
  `tickets/fetched=2026-09-30/origin=MOW/MOW-ANY__2026-11-12__16-31-35Z.parquet`,
  окно — `…/MOW-ANY__2026-11-12..2026-11-13__07-48-40Z.parquet`,
  серии планировщика с коридором цен и с пустым origin —
  `tickets/fetched=2026-09-30/origin=ANY/ANY-SEL__2026-11-12__min=20000,max=40000__16-32-01Z.parquet`
  (фоновый сборщик серий `ANY→X` не создаёт: у билета есть origin, обратная сторона
  дублирует). Почему не по дню вылета: файл окна покрывает до 60 дней, а однозначно у
  файла только когда и по какому городу его загрузили; день вылета — колонка (row group
  на день). Файлы только дописываются, старое уходит целыми папками `fetched=`.
  В пути — город запроса (MOW), аэропорты — колонками (`origin_airport`,
  `destination_airport`, цепочка пересадок). До 30.09.2026 раскладка была
  `date=<день вылета>/origin=`; перенос — `python -m collector.migrate` отдельным `docker run`
  (деплой не обрывает; прерванный — повторный запуск доделывает): копия в бакете →
  ключ в индексе → удаление старого; `parse_file_key` понимает обе.
  Файл пишется сразу по готовности серии; повторная выборка — новый файл рядом
  (история цен), пустая серия — пустой файл («читали, ничего нет»). Колонки плоские
  (origin, destination, departure_at, price, airline, …, `observed_at`) плюс
  `legs_json`, `transfer_points_json`, `chain_json`; `from_row` восстанавливает
  словарь `normalize_ticket` один в один. Мерж/компакция не нужны.
- **Индекс** (`collector/index.py`, SQLite `COLLECTOR_DB`): серии (когда получена,
  страниц, билетов, файл + row group, ошибка), файлы (объём для ретеншна), города
  (все origin/destination из билетов — список для сборщика). Потерян индекс →
  при старте файлы озера импортируются в учёт объёма (без серий).
- **Ретеншн**: раз в `LAKE_RETENTION_INTERVAL` (30 мин) объём `tickets/` по индексу
  сравнивается с `LAKE_MAX_GB` (180); выше — удаляются файлы с самым старым моментом
  загрузки до 95 % порога, их серии выпадают из индекса. Lifecycle Object Storage умеет только по
  возрасту, поэтому по размеру чистим сами; `max_size` бакета 200 ГБ — аварийный потолок.

### HTTP API (порт 8001, только внутри compose-сети)

| Ручка | Что |
|---|---|
| `POST /v1/fetch` | одна серия `{origin, destination, day, value_min, value_max, direct, with_baggage, max_pages, client, ttl_seconds, wait}` → задание `{id, status, pages, tickets, cached, error}` |
| `GET /v1/requests/{id}?wait=` | статус (long-poll до `wait` с) |
| `GET /v1/requests/{id}/result` | `{tickets, pages, exhausted, error, cached}` — билеты отдаются один раз; `?format=arrow` — Arrow IPC-поток в схеме озера, метаданные в заголовке `X-Series-Meta` (так берёт планировщик: разбор по колонкам `core/series_arrow.py`, ~0.2 с на серию MOW→ANY против ~1.1 с через JSON) |
| `POST /v1/batch` | список серий, `client: crawl`; у серии может быть `day_to` — окно дат |
| `GET /v1/series/exists` | свежая ли серия (оценка объёма в планировщике) |
| `GET /v1/coverage?params_key=&destination=` | `[origin, day, fetched_at, pages, tickets, exhausted, error]` |
| `GET /v1/cities` | известные города по числу билетов |
| `GET /v1/stats`, `POST /v1/stats/crawler` | счётчики очереди/страниц/429/кэша, сводка сборщика |
| `GET/POST /v1/crawler/state` | номер и начало прохода сборщика (переживает рестарты) |
| `GET /v1/lake/files?since=`, `GET /v1/lake/file?key=` | файлы озера по индексу и их байты (отладка; склад планировщика читает S3 сам) |

## Фоновый сборщик (`crawler/`)

Отдельный процесс без данных, токена и S3: только планирование поверх индекса
коллектора. Раз в `CRAWL_TICK_SECONDS` (2 мин):

1. Города = стартовые хабы `CRAWL_SEED_CITIES` ∪ `/v1/cities` (все origin/destination
   из уже собранных билетов, по убыванию числа билетов) — список растёт сам.
2. Покрытие `/v1/coverage` (серии `X→ANY` без коридора) и очередь `/v1/queue`.
3. **Проход по календарю** (`crawler/schedule.sweep`, с 02.10.2026 вместо срочности
   «возраст / цель»): курсор идёт по дням вылета от сегодня до `CRAWL_HORIZON_DAYS` (180).
   На каждом дне в очередь встают запросы всех городов, у которых этот день ещё не
   обработан в текущем проходе, по порядку городов (хабы и крупные раньше). Пара
   обработана, если серия получена не раньше начала прохода `pass_started` (с ошибкой
   источника — тоже; повтор в следующем проходе). Курсор = первый день, где есть
   необработанная пара (`sweep_day`/`sweep_offset` в сводке): левее него все города
   обработаны. Новый город посреди прохода догоняется с начала горизонта. Город, у
   которого только ошибки (≥ 3), в карантине — одна проба (сегодня) за проход.
4. **Окна дат**: запрос начинается с дня курсора и захватывает столько следующих
   необработанных дней, сколько влезает в `CRAWL_WINDOW_TICKETS` (10 000 билетов ≈ 25
   страниц) / плотность города (p90 билетов в день по его покрытию); город без покрытия —
   `CRAWL_UNKNOWN_WINDOW_DAYS` (30). Москва идёт окнами по 1–2 дня, город с парой билетов
   в день — одним запросом на весь горизонт; когда курсор доходит до уже покрытых дней,
   запроса не нужно. Скорость упирается в страницы по 400 билетов: потери только на
   неполной последней странице (~2 % у окна в 25 страниц). `CRAWL_WINDOW_TICKETS=0` — по
   одному дню.
5. **Круг**: дошли до конца горизонта — проход окончен, следующий сразу начинается с
   сегодняшнего дня (`CRAWL_MIN_PASS_HOURS` — пауза от начала предыдущего, по умолчанию 0;
   до 04.10.2026 было 24 ч, и проход за ~полсуток оставлял ручку простаивать остаток суток).
   Чаще проходы — быстрее растёт озеро: ретеншн по `LAKE_MAX_GB` раньше срезает старые
   снимки (короче история на `/dynamics`). Номер и начало прохода хранит коллектор
   (`GET/POST /v1/crawler/state`, таблица `kv` индекса) — рестарт не сбрасывает проход.
   Запросы подаются с `ttl_seconds` = время с начала прохода: серия, полученная в этом
   проходе (в том числе приложением), — кэш, остальное — в источник.
6. В очередь `crawl` подаются окна по календарю, пока в ней не наберётся
   `CRAWL_QUEUE_PAGES` (1800, ~30 мин работы ручки) **оценочных страниц** — средняя
   плотность города × дни окна / 400, — но не больше `CRAWL_QUEUE_TARGET` (3000) окон.
   Дни окон, уже стоящих в очереди, не подаются повторно. Очередь живёт в памяти
   коллектора: после его рестарта (деплой) она пуста, сборщик заполняет её за тик.
   Сводка (номер и курсор прохода, обработано / ждут / нет данных / ошибок, окон,
   оценка страниц в очереди и поданных) уходит в `/v1/stats/crawler`.

Бюджет (замер по индексу 30.09.2026, 2782 города, 41 день): посуточно — ~3 100 страниц
на день горизонта (94% серий — одна страница, 62% пустые); окнами — ~640, почти ровно
«все билеты / 400». Пустой город стоит одну страницу на весь уровень свежести.
Запросы приложения идут вне очереди.

## Метрики и дашборд (`collector/metrics.py`, `analytics/`)

Коллектор раз в `METRICS_INTERVAL_SECONDS` (60) снимает строку ops-метрик: нагрузка
машины из `/proc` и statvfs тома, объём озера (индекс) и бакета (листинг S3 раз в
интервал ретеншна), очередь по приоритетам, за минуту — страницы/серии/попадания
в кэш по клиентам, 429, ошибки источника/сети/записи, задержка ответа приложению,
число серий, возраст данных сборщика (медиана, p95, максимум — только пары X→ANY на
дни вылета от сегодня: прошедшие дни и пары приложения не обновляются), города,
сводка сборщика. Каждые `METRICS_FLUSH_ROWS` (2) строки дописываются в файл часа
`ops_metrics/date=YYYY-MM-DD/<HH>-00-00.parquet` (перезапись), прошедшие дни
склеиваются в `ops_metrics/date=YYYY-MM-DD/day.parquet` (раз в час и при старте —
вместе с мелкими файлами прежней раскладки): ClickHouse читает файл одним GET, и
сотни файлов в сутки тормозили дашборд на 15–20 с.
Раз в `COVERAGE_SNAPSHOT_SECONDS` (600) перезаписывается `coverage/latest.parquet`
(город × день вылета: когда получено, возраст, страниц, билетов, ошибка и её текст —
`series.error_msg` индекса).
`METRICS_ENABLED=0` выключает.

Дашборд «Flights · Коллектор» живёт в общей Grafana observatory
(https://grafana.sereshotes.dev; ClickHouse читает Parquet из бакета по named collections):
`analytics/README.md`, `analytics/observatory.yaml`. У flights своя база, пользователи
ClickHouse, источник данных и папка Grafana — другие проекты не трогаются.

## Планировщик

`api/worker.make_ticket_fetch`: при `COLLECTOR_URL` серии берутся через
`core/collector_client.CollectorClient.fetch_series` (тот же контракт, что у
`graphql_api.fetch_series`: прогресс на каждую страницу, `cached` → «из кэша» в
степпере). Без `COLLECTOR_URL` — прежний прямой GraphQL с `ticket_cache` (локальный
запуск, тесты). С коллектором таблица `ticket_cache` при старте удаляется.

## Деплой

- Образы: `flights-planner`, `flights-collector`, `flights-web` (GitHub Actions
  `.github/workflows/deploy.yml`).
- Прод-compose `deploy/compose.prod.yml` едет внутри образа planner; `run.sh` на VM
  при каждом обновлении копирует его в `/opt/flights/docker-compose.yml`, так что
  состав контейнеров меняется обычным деплоем (cloud-init выполняется один раз).
- Terraform: `bucket_max_size_gb` 200, в `.env` VM — `PLANNER_IMAGE`, `COLLECTOR_IMAGE`,
  `LAKE_MAX_GB`, `RATE_PER_MINUTE`. `terraform apply` на существующей VM меняет только
  бакет и metadata (VM не пересоздаётся).
- **Одноразово на уже созданной VM**: `deploy/vm-migrate.sh ubuntu@<ip>` — дополняет
  `.env`, заменяет `run.sh`, останавливает старый стек, сжимает `flights.db` без
  `ticket_cache` (`scripts/shrink_planner_db.py`, VACUUM INTO — обычному VACUUM не
  хватило бы диска) и поднимает новый.

Проверка после выкатки: `https://flights.sereshotes.dev/api/health` содержит блок
`collector` (`status: ok`, очередь, серии, объём озера); джоба планировщика идёт
через коллектор; в бакете появляются `tickets/fetched=…/origin=…/*.parquet`.
