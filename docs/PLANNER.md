# Планировщик маршрута (страница `/planner`)

Альтернативная страница поверх текущего пайплайна — **планировщик цепочки городов**
`A → B → C → …`. Живёт рядом с классическим поиском «туда-обратно» (`/`, `/results`),
его не заменяет. На проде: <https://flights.sereshotes.dev/planner>.

Статус: **v1 на моках** (весь сбор и построение цепочек — фиктивные, см. «Что осталось»).
Контракт типов уже заложен под будущий backend.

## Идея / поток

Одна страница, сверху вниз:

1. **Скелет маршрута.** Столбец остановок. На каждой:
   - набор **городов-кандидатов** (можно несколько на выбор) либо **«любой»** (wildcard);
   - **диапазон дат** — «в какие даты нам ОК быть в этом городе» (только у промежуточных;
     у первого/последнего города дат нет — они выводятся из соседних).
2. **Оценка + загрузка.** Рядом с кнопкой «Загрузить данные» — сколько запросов к API
   потребуется. Жмём → прогресс сбора.
3. **Детальные фильтры** (после сбора), по порядку:
   - по городу: мин/макс дней, обязательное окно дат «покрыть», «оба выходных»;
   - по переходу: число пересадок, суммарная длительность перелёта;
   - в конце — общий фильтр «длина всей поездки».
   Ниже — карточки цепочечных маршрутов.

## Принятые решения

| Тема | Решение |
|---|---|
| Размещение | Отдельная страница `/planner`, классический поиск не трогаем |
| Wildcard «любой» | Концы маршрута — конкретные города; «любой» только в середине; два «любых» подряд запрещены; один и тот же единственный город дважды подряд запрещён |
| Несколько городов на пункт | Остановка — набор городов-кандидатов (`kind: 'cities'`, `airports[]`) либо `kind: 'any'` |
| Даты | Диапазон «когда ОК быть здесь» только у промежуточных; концы выводятся из соседей. Везде — календарный `DateRangePicker` (и в скелете, и в фильтрах) |
| Язык названий | Названия городов — **на английском** везде (автокомплит `core/airports.py` отдаёт EN; поиск по-русски работает) |
| Стоимость сбора / авто-ANY | per-date `prices_for_dates`; плечо собирается **одним «якорным» запросом в день** по стороне с меньшим числом городов (`origin=X,dest=None` или `origin=None,dest=Y`), другая сторона — фильтр по выбранным городам. Поэтому конкретные города **не дороже «любого»** |
| month-matrix | **Отвергнут** как источник сбора: не фильтрует по пересадкам (`direct` инертен), отдаёт одно самое дешёвое в день → нет гарантии «прямого» и фильтра по пересадкам. Возможен позже как опциональный «быстрый предпросмотр самой дешёвой цены» |

Модель стоимости плеча (per-date): `requests = min(|A|, |B|) × дни`, где `|·|` — число
городов на стороне, «любой» = ∞ (нельзя заякорить). Хотя бы один конец всегда конкретен
(правила выше), поэтому якорь конечен. Пример: `TAO(1) → MOW/EVN(2)` = 1 запрос/день,
`MOW/EVN(2) → ANY` = 2 запроса/день.

## Архитектура (frontend)

Всё под `frontend/src/planner/`:

- `types.ts` — контракт (`PlannerStop`, `PlannerRequest`, `PlannerEstimate`, `CityFilter`,
  `TransitionFilter`, `PlannerFilters`, `Itinerary`, `CollectState`). Формы рассчитаны на
  будущий backend (`POST /api/plan/estimate`, `/api/plan/gather`).
- `validation.ts` — правила корректности скелета.
- `dates.ts` — дата-арифметика (окна, покрытие, выходные).
- `mock.ts` — **мок-«бэкенд»**: `estimatePlan` (оценка запросов), `generateItineraries`
  (правдоподобные цепочки), `runMockCollection` (фейковый прогресс). Пул городов для
  раскрытия «любой» — здесь же.
- `filtering.ts` — клиентская фильтрация цепочек + дефолтные фильтры/границы.
- `components/` — `RouteSkeleton`, `PlanEstimateBar`, `CollectProgress`, `FiltersPanel`,
  `CityFilterCard`, `TransitionFilterCard`, `TripLengthFilter`, `ItineraryCard`.
- `pages/PlannerPage.tsx` — оркестрация состояния (idle → collecting → ready).

Переиспользуются общие: `components/AirportCombobox`, `components/DateRangePicker`,
`data/airports` (автокомплит), стили `styles.css` (тёмная тема, класс-префикс `pl-`).

## Что осталось (roadmap до «боевого»)

1. **Реальный backend сбора.** `POST /api/plan/estimate` + `/api/plan/gather` (джоба с
   прогрессом). Обобщить `core/collector.py` с 2-плечевого stopover на N-плечевую цепочку
   с авто-ANY якорингом (сборка плеч независимо + join по общему городу, как в текущем
   стыковочном сборщике).
2. **Движок построения цепочек.** Обобщить `core/aggregate.find_combinations` с 2 плеч на N
   (поиск путей по времени-расширенному графу «город × дата» с учётом окон пребывания).
3. **Подключить фронт к реальному сбору** вместо `mock.ts` (прогресс через таблицу `jobs`,
   как в классическом потоке).
4. **Кэш/персист** собранного (SQLite + Parquet-озеро — как в остальном проекте).

Возможные доработки:
- Режим «предпочитать прямые» — для нужных плеч собирать per-date с `direct=true`
  (реальный фильтр «только прямые», ценой большего числа запросов).
- month-matrix как опциональный «быстрый предпросмотр самой дешёвой цены» (без фильтров).
- Пересмотр запрета «два любых подряд», если появится способ его собирать.
