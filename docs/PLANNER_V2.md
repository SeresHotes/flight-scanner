# Планировщик v2 — единственный режим, все вычисления на бэке, GraphQL

Статус: **реализовано** 2026-09-27 (PR #66–#71, все шаги ниже). Раздел «Что есть
сейчас» описывает состояние ДО переработки и оставлен как история; актуальные
отличия от плана: остановки и условия редактируются одним списком
(`planner/components/QueryEditor`); оценку с учётом кэша отдаёт бэк
(`POST /api/plan/estimate`: requests/cached/cold), предохранитель «слишком
широко» — по холодным страницам (2000); `maxResults` из запроса убран — джоба
строит 5000 самых дешёвых цепочек, а маршруты выбранных наборов строятся по
требованию из сохранённых рейсов джобы (`plan_flights`, до 2000 на набор);
IndexedDB-кэша нет, статус джобы отдаёт только прогресс и сводку.

## Цель (формулировка продукта)

1. Классический режим («туда-обратно», `/`, `/results`) убираем. Приложение —
   только планировщик, он живёт на `/`.
2. Пользователь сначала задаёт **единый набор фильтров**: скелет маршрута
   (остановки, окна дат) + все детальные фильтры (пересадки, длительность,
   багаж, дни в городе, длина поездки, потолок цены). Одна форма, один запрос.
3. Если хотя бы в одной остановке «любой город» или несколько городов —
   открывается **режим городов**: список наборов городов под фильтры.
   Иначе сразу **режим маршрутов**.
4. В режиме городов можно **отметить несколько наборов** и кнопкой перейти на
   страницу маршрутов, где показаны маршруты **всех отмеченных наборов вместе**
   (сравнение).
5. **Все вычисления — на бэке**: сбор недостающих данных, наборы городов,
   маршруты, фильтрация, пагинация. Фронт только рисует.
6. Источник — **GraphQL Data API** (`prices_one_way`): все билеты на дату, а не
   один самый дешёвый на направление; сегменты, пересадки, багаж явными полями.
7. Фильтр по **багажу на каждое плечо**; на карточке — плашка про багаж и все
   пересадки (аэропорт, длительность, ночная, виза).
8. **Hidden-city** в планировщике «честно»: из полного списка билетов A→ANY,
   а не по случайным попаданиям.

## Проверенные факты о GraphQL (живые запросы 27.09, в т.ч. в этой сессии)

`POST https://api.travelpayouts.com/graphql/v1/query`, заголовок `X-Access-Token`
(тот же токен), `prices_one_way(params: ParamsOneWay, paging{limit≤400, offset},
grouping: NONE, sorting: VALUE_ASC)`. 60 запросов/мин. ~0.6–1.5 с на страницу.

- **Город → ANY работает** (без `destination`), **ANY → город работает**
  (без `origin`), страна→город работает (`origin_type: COUNTRY`). Страна→страна и
  запрос без обоих концов — ошибка. Список стран/городов в одном поле — ошибка.
- Отдаёт **все** билеты: прямые и с пересадками вместе (режим `direct` не нужен),
  `segments.transfers{at, duration_seconds, night_transfer, visa_required, country_code}`,
  `flight_legs{origin, destination, departure_at, arrival_at, flight_number}` с
  таймзонами, `baggage_code` (`0PC`, `1PC20`, `1PC`…), `with_baggage`,
  `ticket_link` (тот же `t=`, префикс `https://www.aviasales.ru/search`).
- `trip_duration` приходит **0** — длительность считать по `flight_legs`.
- Пагинация: `offset` ограничен (~14 800 → «too high paging depth», ≈37 страниц).
- Объёмы за один день (15.10.2026):

| Запрос | Страниц | Билетов | Замечание |
|---|---|---|---|
| MOW → SEL | 1 | 19 | (3 дня — 55) |
| ANY → SEL | 4 | 1 386 | 127 городов вылета; Москва появляется с 36 127 ₽ |
| ANY → SEL, 7 дней | >8 | >3 200 | за 8 страниц до Москвы не дошли — окно дат тянуть нельзя, ходим по дням |
| MOW → ANY, без коридора | >12 | >4 800 | 432 направления, до 66k ₽ и не исчерпано |
| MOW → ANY, `value 20–60k` | 4 | 1 568 | коридор по цене режет объём в разы |

Вывод: сортировка по цене + лимит 400 означают, что для ANY-плеча нужна либо
пагинация «пока не исчерпано» (10–20+ страниц в день), либо **ценовой коридор**
(`value_min/value_max`). Потолок цены из единых фильтров — естественный `value_max`.

## Целевая архитектура

```
React (только планировщик)                FastAPI
 /            форма: скелет + фильтры  ──POST /api/plan/run──▶  джоба (dedup по хэшу запроса)
 /jobs/:id    прогресс                 ◀─GET  /api/plan/jobs/:id─   fetch (GraphQL, кэш 24ч)
 /combos/:id  наборы, мультивыбор      ◀─GET  …/combos?…──────────   core/overview.py (DP)
 /routes/:id  маршруты (по наборам)    ◀─GET  …/routes?combos&page─  core/planner (A*) + materialize
```

### 1. Единый запрос `PlanQuery` (контракт фронт ↔ бэк)

```
stops[]:        {kind: cities|any, codes[], window[start,end]}         # как сейчас
cities[]:       {minStay, maxStay, mustCover|null, requireWeekend}      # == stops
legs[]:         {maxTransfers, minLayoverMin, travelMin[lo,hi],
                 depTime[lo,hi], arrTime[lo,hi],    # время суток вылета/прилёта, местное, мин; [0,1440] = любое
                 baggage: any|included|none, hiddenCity: bool}          # == stops-1
tripLength[lo,hi], maxResults            # maxCost (бюджет) удалён 01.10.2026
```
Фильтр `allowedCodes` из старых фильтров исчезает: сужение по городам делается
выбором наборов на странице `/combos`. Запрос сериализуется в URL целиком
(`urlState.ts` расширить), хэш запроса — ключ джобы и кэша результата.

### 2. Сбор: `core/graphql_api.py` + новый `collect_plan`

- `fetch_tickets(origin|None, destination|None, day, value_min, value_max,
  with_baggage, direct) -> list[Ticket]` — пагинация до исчерпания или до
  `MAX_PAGES_PER_DAY`; `fetch_cache` v2 с ключом `(source, origin, dest, day,
  value_min, value_max, page)`, TTL 24 ч.
- Нормализация `Ticket` в единый формат рейса (замена dict из REST):
  `origin/dest (город и аэропорт), departure_at, arrival_at (реальный), duration
  (по legs), transfers[] {at, city, minutes, night, visa}, legs[], airline,
  price, baggage {known, included, pieces, kg}, link, hidden_city|null`.
- Якорение как сейчас (сторона с меньшим числом городов), но:
  - город→город: 1 запрос/день (все билеты, прямые включены) — **дешевле, чем
    сейчас** (было 2);
  - город→ANY / ANY→город: страницы с коридором `value_max = maxCost` (или
    остаток бюджета: `maxCost − нижняя оценка остальных плеч`), без потолка —
    `MAX_PAGES_PER_DAY` (предложение: 12 → до 4 800 билетов/день);
  - фильтры, которые источник умеет (`direct`, `with_baggage`), передаём в запрос —
    объём страниц падает.
- **Hidden-city** (флаг в фильтре плеча): для плеча A→B из **A→ANY** берём билеты,
  у которых B — любая пересадка (не только первая) и цена ниже лучшего A→B того
  дня; виртуальный рейс: прилёт в B **реальный** из `flight_legs`, `transfers` =
  позиция B − 1. **Багаж:** берём как по билету (`baggage_code`), фильтр по
  багажу считает такой рейс по данным билета; на карточке рядом с иконкой
  багажа — «!» с подсказкой «hidden-city: багаж может улететь в конечный пункт
  билета». Никаких эвристик про таможню. Если плечо якорится по A,
  A→ANY уже есть; если по B — добавляем A→ANY с `value_max = лучший A→B`
  (2–4 страницы/день на город A). Для ANY-плеча A→ANY даёт hidden-city
  во **все** промежуточные аэропорты бесплатно.
- Оценка запросов (`estimate`) пересчитывается по новой модели:
  `город→город: дни × 1 (+2–4 hidden)`, `ANY: дни × ожидаемое число страниц`.
  Ожидаемое число страниц берём из статистики `fetch_cache` по этому городу,
  иначе константа.
- Сохранение: `quotes` → новая таблица `tickets` (плюс `segments_json`,
  `baggage_code`, `arrival_at`, `source`); озеро Parquet — те же поля.
  Граф пересадок (`core/transfer_graph.py`, `/api/graph/*`, `scripts/scan_any.py`,
  `scripts/hidden_city.py`, `scripts/build_transfer_graph.py`) планировщику не
  нужен: тот же ответ («через что бывают пересадки», hidden-city) даёт A→ANY в
  момент запроса, полнее и без предварительного сбора. Удаляется в PR чистки.
  Контейнер `flights-scan` на VM продукту тоже не нужен (он кормил граф);
  останавливать ли его — решение пользователя.

### 3. Построение на бэке

- **Фильтры плеча** (пересадки, мин. пересадка, длительность, багаж, hidden-city)
  применяются к списку рейсов **до** построения — таблица рейсов сразу меньше.
- **Фильтры города** (дни, окно, выходные) — в `_onward_candidates` A*, а не после;
  `tripLength` — при выдаче. Лишние ветки не раскрываются.
- **Наборы городов** — `core/overview.py`, порт `planner/overview.ts`, но по
  **дням**, а не по точному времени (A* и так стыкует по дате: `dep_day ≥ arr_day`):
  состояние = вектор по дням прилёта, расширение префикса на все города следующего
  плеча — групповая свёртка (numpy) по рёбрам `(from → to)`. Выход как сейчас:
  `{codes[], minPrice, transfersAtMin, minTransfers, count}`. Риск: Python
  медленнее JS-воркера (1.7 с на MOW→any→SEL→any→MOW); критерий приёмки —
  ≤ 5 с на этом запросе, иначе кэшировать по хэшу запроса и считать в джобе.
- **Маршруты** — текущий A*, результат `compact-v1` **остаётся в БД джобы**, фронту
  не отдаётся целиком: `GET …/routes?combos=A-B-C,A-D-C&offset=0&limit=50`
  материализует страницу (`_assemble`) с полными сегментами (багаж, пересадки,
  hidden-city). Фильтр по наборам — по кодам городов цепочки.
- Джоба = рейсы по остановкам: дедуп по `PlanQuery.collect_key` (виды, города,
  окна, радиус), TTL 24 ч. Фильтры и бюджет на сбор не влияют — страницы результата
  передают их параметром `f`, вид под фильтры стыкуется из сохранённых рейсов
  (кэш в памяти по `view_key`). Правка фильтра = та же джоба, только стыковка.

## Риски и допущения

1. **Стоимость ANY-плеч.** Без потолка цены MOW→ANY — 12+ страниц в день; 7 дней ≈
   100 запросов ≈ 2 мин на плечо при 60/мин. С `maxCost` — в 3–4 раза меньше.
   Допущение: показывать оценку и настойчиво предлагать потолок цены; жёсткий
   потолок страниц в день.
2. **Наборы городов в Python.** Порт DP может оказаться на порядок медленнее
   воркера. План: дневная гранулярность + numpy; замер на MOW→any→SEL→any→MOW
   до перехода к UI.
3. **Интерактивность фильтров.** Сейчас движение слайдера — мгновенно на фронте;
   станет запросом к бэку (секунды на построение при 100k+). Смягчение: дебаунс,
   кэш джоб по хэшу, `maxResults` по умолчанию ниже (наборы городов покрывают
   ширину).
4. **Память VM 4 ГБ.** Билеты GraphQL тяжелее (сегменты). Держим их в SQLite, в
   RAM — только `_FlightTable` (массивы) и compact-результат; `MAX_PAGES_PER_DAY`
   ограничивает объём.
5. **Hidden-city и багаж.** Решение пользователя: только «!» у иконки багажа,
   без оценок «выдадут / не выдадут». Правила Aviasales/Travelpayouts к таким
   ссылкам не проверены.
6. **Data API ≠ live.** «Все рейсы» = все билеты из кэша пользовательских поисков
   с лагом до суток, не расписание.
7. Два старых падения в `tests/test_job_stages.py` — в main до этой работы.
