# Исследование: нижняя оценка хвоста по «город + день» (задача 6 ТЗ «склад билетов»)

Дата: 2026-10-01. Код прототипа — ветка `research-lb-day` (в прод не идёт):
`planner/src/search.rs` (`completion_lb_day`, `day_lb_get`, счётчики `ST_*`, переключатель
`RESEARCH_DAY_LB`), `planner/src/overview.rs` (та же оценка в отсечении наборов),
`planner/examples/lb_research.rs` (запуск обоих режимов на сохранённых рейсах джобы).

## Вопрос

Текущая нижняя оценка хвоста `completion_lb` — по городу без дат: lb[i][город] = минимальная
цена добраться с остановки i до финала. На запросах с 2–4 «любыми» подряд рейсов много
(сотни тысяч), а стыковка требует вылета строго в следующий день — не слабеет ли оценка так,
что перебор маршрутов (A*) и обход наборов тратят шаги на пути без продолжения по датам?

Прототип: lb2[i][(город, день прилёта)] = минимум по рейсам из города с вылетом строго позже дня
прилёта (price + lb2 хвоста по дню прилёта рейса); хранится списком (день вылета, суффиксный
минимум) на город, запрос — бинарный поиск. Оценка admissible и consistent (это точное решение
ослабленной задачи на состояниях «город × день», рёбра настоящей задачи — подмножество).
В ленивом A* ключ кандидата price + lb2(dest, день прилёта рейса) не зависит от узла, поэтому
списки кандидатов по (плечо, город) остаются общими — структура поиска не меняется.
В наборах — та же оценка в предварительной (по лучшему рейсу группы) и точной (по ячейкам
состояния) границе отсечения.

Доля «мёртвой» работы при оценке по городу: мёртвых узлов 3 % (q3) и 38 % (q2) от созданных;

число извлечений падает лишь на 4–7 %, а время — не меняется (миллисекунды в обоих случаях).

## Где на самом деле время

Джоба q3 на проде шла 102 с, из них A* + наборы — 0.05 с. Остальное — загрузка 450 тыс. рейсов
из склада (плечо ANY → ANY: X→ANY всех городов, куда есть рейсы из MOW, за 3 дня; ~500 МБ
Arrow) и запись Parquet джобы. Запрос с четырьмя «любыми» подряд (q4) упал на выборке среднего
плеча (все города × 3 дня, > 500 тыс. строк, таймаут склада на HDD). Узкое место — объём
данных плеч «любой → любой» и диск склада, а не нижняя оценка.

## Рекомендация: **не делать** (оценку по городу + дню в прод не вносить)

- Выигрыш по шагам 4–7 % при времени стыковки в десятки миллисекунд — ниже порога
  заметности; память прототипа мала (десятки КБ), но и экономить нечего.
- Корректность доказуема (admissible, consistent), ответы совпали — техрисков нет, но и
  пользы нет; переезды к соседям (radius) в прототипе не учтены — пришлось бы дорабатывать.
- Усилия стоит направить на объём данных плеч «любой → любой»: порядок сбора от концов к
  середине (оба конца среднего плеча ограничены соседями), явный лимит выборки с понятной
  ошибкой вместо молчаливого усечения, компактная выдача склада для перебора (без сегментов
  и ссылок; полные сегменты — только для рейсов итоговых маршрутов) и SSD под Postgres.
  Это отдельные задачи вне данного исследования.
