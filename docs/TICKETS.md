# Склад билетов в памяти планировщика (`planner/src/lakestore.rs`, `lakesync.rs`)

Текущее состояние всех билетов из серий **X→ANY** озера коллектора — прямо в памяти
планировщика, в компактном виде: блок на серию «город вылета × день», новая серия целиком
заменяет блок своего дня. Планировщик берёт рейсы отсюда за один проход на плечо вместо
сотен серий через коллектор. Озеро в S3 — источник истины (история, аналитика); склад —
производная от него, восстанавливается целиком.

```
collector ──запись файла──> S3: tickets/fetched=<день загрузки>/origin=<город>/<A>-ANY__<дни>__<время>.parquet
                                   │  список + GET (SigV4, те же S3_* из .env)
planner ──lake-sync──> склад в памяти (блоки серий) ──> сбор джобы (TicketStore)
   └── снапшот /app/data/store.snap (раз в час; рестарт — секунды вместо загрузки озера)
```

До 01.10.2026 склад был отдельным сервисом `tickets` (Rust) с Postgres `tickets-db`:
~1,3 КБ на строку, 26 ГБ с индексами на отдельном SSD, холодная выборка 0,4–2,5 с, а
рейсы джобы ещё раз копировались в память планировщика. Сервис, его Postgres и пуш
файлов из коллектора удалены.

## Данные

- **Блок** (`lakestore::Block`) = серия X→ANY «город вылета × день»: момент загрузки
  (`fetched` — из имени файла), горячие колонки — город вылета и прилёта билета номерами
  словаря кодов (u32) и цена (f64), холодная часть — все поля билета в схеме озера
  (`collector/lake.SCHEMA`: концы, времена, длительности, авиакомпания, ссылка, багаж,
  `legs_json`, `transfer_points_json`, `chain_json`, `search_*`) **по колонкам** (длины, затем
  байты — одинаковые значения рядом), сжатая zstd. Пустые дни окна — тоже блоки (0 билетов:
  день покрыт, в GraphQL не идём).
- **Выборка** (`select`): по диапазону дней — блоки из `BTreeMap<(день, город), блок>`, по
  горячим колонкам — номера подходящих строк (без разбора), потолок строк проверяется
  до разбора; разжимаются только блоки с совпадениями, а разбираются только выбранные
  строки. Порядок результата — день, город вылета, цена (как у прежнего склада).
- **Объём**: синтетический замер (`cargo test --release --lib bench_store -- --ignored
  --nocapture`) — ~100 Б на билет в памяти (сырая холодная часть ~620 Б), применение
  ~2 мкс на строку, ANY→Y за неделю и 10 городов → ANY — десятки мс. На 18,7 млн билетов
  (01.10.2026) это ≈ 1,9 ГБ; реальный размер — `memory_mb` в `/api/health` → `tickets`.

## Как серии попадают в склад

1. **Старт**: снапшот `LAKE_SNAPSHOT_PATH` (по умолчанию `store.snap` рядом с БД, на VM
   `/opt/flights/data/store.snap`) — склад готов сразу после чтения файла. Без снапшота
   (первый запуск, другая версия формата) — после первого полного прохода; джобы ждут
   (до 30 мин), оценка `/api/plan/estimate` пока считает без склада.
2. **Полный проход** — на старте и раз в `LAKE_FULL_SYNC_SECONDS` (6 ч, страховка):
   список всего `tickets/`, по каждому (город, день) не раньше вчера — самый свежий файл;
   качаются только файлы, у которых есть день новее склада (`lakesync::plan_files`), в
   `LAKE_SYNC_WORKERS` (16) потоков.
3. **Дельта** раз в `LAKE_SYNC_SECONDS` (120): список `tickets/fetched=<сегодня>/` и
   `<вчера>/` (UTC) — файлы раскладываются по дню загрузки, новые появляются только там.
4. **Применение** (`LakeStore::apply`): по каждому дню окна файла — если в складе серия не
   новее, блок дня заменяется. Журнал файлов не нужен: файл, чьи дни в складе не старше
   его, просто не качается; повтор ничего не меняет, более старый файл на обновлённый
   день пропускается. Файлы ANY→Y, A→B и с ценовыми коридорами (запросы приложения) в
   склад не идут.
5. **Ретеншн** после каждого прохода: дни вылета раньше вчера (UTC) — вон.
6. **Снапшот** — сразу после загрузки с нуля и раз в `LAKE_SNAPSHOT_SECONDS` (3600), если
   склад менялся: словарь кодов и блоки как есть, через временный файл и rename.

S3 — без SDK: список (`ListObjectsV2`) и GET с подписью SigV4 (`lakesync::S3Lake`, сверено с
botocore). Локально вместо S3 — каталог `LAKE_LOCAL_ROOT` (тот же, что у коллектора без S3).
`PLANNER_LAKE=0` — склад выключен (рейсы только сериями через коллектор).

## Планировщик на складе (`planner/src/tickets.rs`, `collect.rs`)

- `TicketStore` — трейт склада для сбора; реализация — `lakestore::SharedStore`, в тестах —
  заглушки. Покрытие (`coverage`, `coverage_days`) считается один раз на джобу.
- Порядок сбора: сначала плечи с конкретным городом — город→город и город→ANY одной
  выборкой X→ANY по городам вылета за окно (прямые A→B и hidden-city из тех же билетов),
  ANY→город — срез по городу прилёта; затем «любой → любой» от концов к середине (каждый раз
  плечо с наибольшим числом собранных соседей).
- В GraphQL через коллектор — только за отсутствующим: X→ANY — (город, день) без серии в
  складе; ANY→Y — дни, по которым в складе нет ни одной серии. ANY→ANY без склада — ошибка.
- Потолок строк одной выборки — `STORE_MAX_ROWS` (600 тыс.): больше — джоба падает с
  понятной ошибкой «слишком широкий запрос».

## Запуск и проверка

- Переменные: `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` (общий
  `.env` VM) или `LAKE_LOCAL_ROOT`; `LAKE_SNAPSHOT_PATH`, `LAKE_SYNC_SECONDS`,
  `LAKE_FULL_SYNC_SECONDS`, `LAKE_SNAPSHOT_SECONDS`, `LAKE_SYNC_WORKERS`, `PLANNER_LAKE`.
- Тесты: `cd planner && cargo test` — кодек и разбор против читателя коллектора, замена
  серий, выборки, ретеншн, снапшот, полный проход и дельта по локальному озеру, подпись
  SigV4; сквозной `tests/e2e.rs` грузит склад из локального озера.
- Проверка на проде: `curl -s https://flights.sereshotes.dev/api/health | jq .tickets` —
  `status: ok`, `series`, `tickets`, `memory_mb`, `sync` (`state`, `last_sync_at`,
  `files_failed`, `snapshot_at`, `loaded_from_snapshot`); в логах планировщика
  `[lake] полный проход: …` и `[lake] склад готов за … с`.
